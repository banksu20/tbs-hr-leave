

### Employee cancellation approvals

Employees use cancellation within **Recent leave history** in their LINE employee dashboard. History shows one entry initially; Show one more reveals one additional entry. Records sort by latest leave date descending (request ID breaks ties), including rejected/cancelled history. Only the latest eligible pending/approved entry can start a cancellation; cancelled/rejected/past entries remain in history without blocking it. Pending leave cancels immediately. Approved future leave creates a separate cancellation request: the original leave, quota usage and Calendar projection do not change while it is pending.

The boss reviews these in **CEO → More → Pending requests → Cancellation requests**. Approving removes only the selected dates; rejecting preserves the leave. Changes to the underlying request expire an outstanding cancellation rather than applying a decision to different details. Decisions and submissions are recorded in change history. Existing Sheet/Calendar workers see changes only after actual cancellation. Calendar edits follow the existing managed-event rules; manually created events are not removed.

Employee requests use server-verified LINE access tokens (channel `2008617589`), resolve linked accounts, and never trust a browser-supplied employee ID. Boss decisions use the dashboard's existing access policy; this feature does not add CEO login. Cancellation decisions use the same database guard in the dashboard and the dedicated CEO LINE confirmation page. Existing LINE leave-approval buttons still decide only the original leave.

Backend installation: apply `n8n/sql/011_employee_cancellation.sql` through an n8n PostgreSQL node, then apply `scripts/patch-employee-cancellations.mjs` to the current workflow and publish. It reuses the authenticated dashboard webhook credential and database credential. Deploy the Vercel app for `/api/cancellations` and the new controls. No new environment variable is needed. Do not expose the n8n shared secret to the browser.

### CEO LINE cancellation messages

The migration defaults message delivery to OFF. Deploy the app's `/cancel-decision` page and updated `/api/cancellations` before enabling it. Then run `n8n/sql/enable-line-cancellations.sql` through the maintenance PostgreSQL node; it queues each still-valid pending request once, and new requests queue automatically. Do not enable before deployment: the message buttons require the new page.

Cards go to Dan's existing CEO LINE account (the account identified in the current workflow). Approve/reject buttons open a confirmation inside LINE. The server verifies the LINE account and a private per-request token; opening a link never changes leave. The first dashboard or LINE decision wins, and later clicks or edited leave refuse the old decision. Tokens stay in a separate table, outside employee history and dashboard list responses. No original leave request buttons are changed. A real CEO LINE click still needs verification after deployment/activation.

The database enforces the same latest-entry/date policy as the UI. Existing pending cancellation decisions retain their original review flow.
